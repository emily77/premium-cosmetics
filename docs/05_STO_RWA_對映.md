# 05 STO＋ 與 RWA 對映（頂級化妝品專案）

版本：v1.0｜建立日：2026-10-25｜對應主計畫 v2.1 第 2、3、7、9 章

## 1 為什麼化妝品專案要接 STO＋／RWA

主計畫的制度核心是「同一代幣多狀態」（STO＋）。化妝品是**實體商品**，
要接進這套制度，必須先解決一個問題：**鏈上的東西怎麼對應到倉庫裡的東西？**

答案就是 RWA（Real World Asset，實體資產上鏈）：
把「批次、庫存、檢驗報告、包裝」變成可驗證的鏈上憑證，
再讓 STO＋ 的狀態機去管理「這些憑證對應什麼權利」。

一句話：**RWA 解決「這是真的」，STO＋ 解決「這能做什麼」。**

## 2 三層架構

```
┌─────────────────────────────────────────────┐
│ 第三層：STO＋ 權利層                          │
│  ST＋（平台使用／社群貢獻／治理）              │
│  ST （投資性流通，本期不啟用）                 │
│  狀態轉換：申請→審查→核定→執行→回執            │
└─────────────────────────────────────────────┘
                    ▲
┌─────────────────────────────────────────────┐
│ 第二層：RWA 憑證層                            │
│  批次憑證 / 庫存憑證 / 檢驗憑證 / 包裝憑證      │
│  上鏈內容：merkle_root + leaf_count（最小化）  │
└─────────────────────────────────────────────┘
                    ▲
┌─────────────────────────────────────────────┐
│ 第一層：實體層                                │
│  原料 → 打樣 → 量產 → 充填 → 檢驗 → 入庫 → 出貨 │
└─────────────────────────────────────────────┘
```

## 3 RWA 實體對映表

| RWA 資產類型 | 實體對象 | 唯一識別 | 上鏈欄位 | 更新時機 |
|---|---|---|---|---|
| `rwa_product` | SKU 主檔 | `sku_code`（如 RA-H03） | `sku_hash` | 新品開發完成 |
| `rwa_batch` | 生產批次 | `batch_id`（如 RAH03-2026W12-01） | `batch_hash` | 每批生產完成 |
| `rwa_inspection` | 檢驗報告 | `report_id` | `report_hash` | 每份報告核發 |
| `rwa_inventory` | 庫存數量 | `batch_id` + `warehouse` | `qty_commitment` | 每日結算 |
| `rwa_packaging` | 包材批次 | `pkg_lot` | `pkg_hash` | 每批包材進廠 |
| `rwa_custody` | 保管移轉 | `custody_id` | `from_hash` / `to_hash` | 每次移轉 |

### 3.1 批次憑證的資料結構

```json
{
  "batch_id": "RAH03-2026W12-01",
  "sku_code": "RA-H03",
  "product_name": "潤澤玻尿酸精華",
  "manufactured_at": "2026-03-16",
  "expiry_at": "2029-03-15",
  "quantity": 5000,
  "unit": "bottle",
  "manufacturer": "安成生化科技有限公司",
  "formula_version": "F-RAH03-v1.0",
  "inspection": {
    "micro": "pass",
    "heavy_metal": "pass",
    "ph": 5.7,
    "viscosity_cp": 12000
  },
  "report_hash": "0x…",
  "merkle_root": "0x…",
  "leaf_count": 12
}
```

> 依決策 D-014：**鏈上公開 payload 只含 `merkle_root` 與 `leaf_count`**，
> 其餘欄位留在內部資料庫，需要時以選擇性揭露（selective disclosure）提供。

## 4 STO＋ 狀態對映

### 4.1 商品購買 → 取得什麼

| 行為 | 記錄位置 | 產生什麼 | 是否可轉讓 |
|---|---|---|---|
| 購買商品 | `ledgers.sales` | 購買紀錄（Purchased） | 不適用 |
| 上傳使用紀錄 | `ledgers.contribution` | 貢獻紀錄（Earned） | 不可轉讓（D-017） |
| 推薦他人購買 | `ledgers.commission` | 代理佣金（與貢獻**分開記帳**） | 依合約 |
| 參與治理投票 | `ledgers.governance` | 治理紀錄 | 不適用 |

**紅線**：社群貢獻與代理佣金**分開記帳**，不得互相抵扣或混算（主計畫第 1 章）。

### 4.2 狀態機

| 狀態 | 名稱 | 可用權利 | 本期是否啟用 |
|---|---|---|---|
| `ST_PLUS_USE` | 平台使用 | 商品兌換、活動資格、教育內容 | 候選（`enabled=false`） |
| `ST_PLUS_CONTRIB` | 社群貢獻 | 貢獻紀錄查詢、治理建議 | 候選（`enabled=false`） |
| `ST_PLUS_GOV` | 治理 | 對拍攝流程、教育內容、社群服務表決 | 候選（`enabled=false`） |
| `ST_INVEST` | 投資性 | 收益權（候選） | **本期不啟用** |

依 D-017：消費者端先「不可轉讓、不承諾轉 ST」。
依 D-005：不先固定發幣總量、兌換價值、回饋比率。

### 4.3 狀態轉換流程

```
申請 → 審查 → 核定 → 執行 → 回執
 │       │       │       │       │
 └───────┴───────┴───────┴───────┴──→ 全部寫入 transitions + audit_events
```

每一步都必須留下：申請人、規則版本、審查者、核定者、執行時間、回執編號。
**過程可重現且不改寫歷史**（論文對照表第 7 項）。

## 6 與外泌體生髮劑專案的接軌

| 面向 | 外泌體生髮劑專案 | 頂級化妝品專案 | 共用方式 |
|---|---|---|---|
| 製造 | 安成生化 | 安成生化 | 同一代工廠、同一 GMP 文件 |
| 法規 | 化粧品登錄＋PIF | 化粧品登錄＋PIF | 共用 PIF 模板 |
| 檢驗 | 微生物、重金屬、安定性 | 同左（＋SPF 實測） | 共用檢驗項目與實驗室 |
| RWA | 批次憑證 | 批次憑證 | 共用 `rwa_batch` 結構 |
| STO＋ | 貢獻紀錄 | 貢獻紀錄 | 共用 `ledgers.contribution` |
| 宣稱限制 | 不得宣稱生髮 | 不得宣稱生髮 | 共用宣稱白名單 |

**結論**：兩個專案不是兩套系統，是**同一套制度、兩條產品線**。
這正是主計畫「同一代幣多狀態」的落地方式。

## 7 本期不做的事

| 項目 | 原因 |
|---|---|
| 主網部署 | 需林總核定（高影響操作） |
| 代幣發行 | D-005：不先固定發行量 |
| 收益權設計 | 需法律定性與專業顧問 |
| 跨境資料傳輸 | D-020：個資、照片、健康資料不出境 |
| 多層代理 | D-021：先只做單層推薦 |
| 商品預售／預購 | 涉及消費者保護與履約保證，另案 |

## 8 驗收證據（本專案要能證明什麼）

| # | 要證明的事 | 驗收方式 |
|---|---|---|
| 1 | 每個 SKU 有唯一主檔且經真人核定 | `products` 查詢 + `approvals` 紀錄 |
| 2 | 每個批次可追溯到檢驗報告 | `batch_id` → `report_hash` |
| 3 | 鏈上只揭露最小資訊 | payload 檢查：只有 `merkle_root`、`leaf_count` |
| 4 | 貢獻與佣金分開 | `ledgers.contribution` 與 `ledgers.commission` 無交叉 |
| 5 | 未核定權利不顯示為可用 | 介面檢查：`enabled=false` 顯示「未核定／候選」 |
| 6 | 狀態轉換可重現 | `transitions` 完整五步紀錄 |
| 7 | 錯誤可被發現與更正 | `assessments`、`appeals`、`audit_events` |
